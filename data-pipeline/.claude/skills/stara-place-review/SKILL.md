# STARA 장소 데이터 검수/보강

STARA는 "도시–아티스트–장소" 성지 데이터를 여러 원본(크롤링 xlsx/json,
팀원이 직접 정리한 블로그 메모)에서 모아 `Data_Preprocessing_Template.ts`
스키마로 정제하는 프로젝트다. 이 스킬은 2026-08-24~25에 서울/부산/인천을
검수하면서 확립한 전체 워크플로우를 재현한다 — **매번 처음부터 판단하지
말고, 아래 순서와 이미 코드에 반영된 정책을 그대로 따른다.**

먼저 `README.md` 전체(특히 "처리 단계", "가장 중요한 규칙", "장소
포함/제외 기준", "MVP 이후: 전국 확장 준비", "현재 진행 상황", "알려진
갭" 절)와 `CLAUDE.md`를 읽어서 현재 어디까지 진행됐는지, 정책이 그 사이
바뀌지 않았는지부터 확인한다 — 이 스킬 문서 자체보다 README.md가 최신
정본이다. 정책이 실제로 바뀌었는데 이 스킬이 구식이면, 스킬 쪽을 README에
맞춰 고쳐라(반대 아님).

## 0. 사전 확인

- `.env`에 `KAKAO_REST_API_KEY`(지오코딩), `GOOGLE_PLACES_API_KEY`(영업시간,
  fill_hours.py 단계에서만 필요) 있는지 확인.
- 대상 도시가 MVP 3개(서울/부산/인천) 안인지, 아니면 "전국 확장 준비"용
  가벼운 스캔 대상인지 먼저 확인(전자는 전체 워크플로우, 후자는 3번 구조
  스캔만 가볍게).
- 새 원본을 추가하는 경우: `raw_data_정인지/*.json`에 같은 스키마(참고:
  `load_manual_places()`, `incheon_naver_blog.json` 예시)로 넣으면 자동
  인식됨. `member` 필드(멤버 개인 성지면 채우기)를 반드시 채울 것 -
  비워두면 그룹 단위로만 잡힌다.

## 1. 후보 생성

**먼저 결정할 것: 이미 검수해둔 도시에 몇 건만 추가하는 건가, 도시를
처음부터 새로 만들거나 원본을 대량으로 바꾸는 건가?**
- 이미 검수해둔 도시(예: 이미 서울/부산을 한 번 정리해뒀는데 새 블로그
  링크 하나 더 생김) → **1b(직접 추가)**를 써라. 전체 재실행은 기존에
  손으로 채운 relation_text_ko/review 메모를 다 날린다(아래 "함정" 참고).
- 새 도시를 처음 만들거나, 원본 자체를 대량으로 고쳤거나(로더 버그 수정,
  카테고리 재분류 등), 아직 사람이 손댄 게 없는 상태 → **1a(전체 재실행)**.

### 1a. 전체 재실행

```bash
python build_dataset.py --geocode --city=<city> --owner=<owner>
```

산출물은 `preprocessed/generated_{cities,artists,places,places_needs_review}_
<city>_<owner>.{json,csv}` (2026-08-25 확정 명명 규칙 - 종류가 맨 앞, 도시/
작성자는 뒤, 구분자는 언더바). 캐시(`preprocessed/.geocode_cache.json`,
`./cache/*.json`)가 있어서 재실행은 대부분 무료/빠름.

이 단계 자체가 이미 처리하는 것(코드에 반영돼 있으므로 재발명 금지):
숙소류/이벤트성 장소 자동 제외(`ACCOMMODATION_LABELS`), 지오코딩 후
재병합(`6b` 단계 - 언어가 달라 처음엔 안 합쳐진 같은 장소를 city_id 채워진
뒤 한 번 더 합침), city 미상 리포트(`dropped_no_city.csv`), 영문 쿼리
매칭 위험 플래그("영문명으로 검색한 매칭"), source_url 신빙성 자동 판정
(`has_credible_citation()` - 아래 4번 참고).

**절대 build_dataset.py를 검수 없이 바로 fill_hours.py에 넘기지 말 것** -
노이즈 후보에 유료 Google API 호출이 나가서 쿼터만 낭비함(README "영업시간
보강" 절 참고).

**⚠️ 이미 검수한 도시를 다시 돌릴 때 반드시 주의할 것** - 이 명령은 매번
원본부터 새로 조립한다. 그 사이 사람이 손으로 채운 `relation_text_ko`
번역과 review CSV의 수동 메모("의심 오매칭" 같은 것)는 코드가 아니라
그때그때 채운 값이라 **원본에 없으면 재실행 시 통째로 사라진다**
(source_url 신빙성 판정만 `has_credible_citation()`이 코드에 있어서
살아남음, 2026-08-25 부산에 새 소스 추가 후 재실행하면서 실제로 8건
번역이 다 날아간 적 있음 - 직전 번역을 기억하고 있어서 바로 복구했지만
항상 그럴 수 있는 건 아님). 대책:
- 재실행 전에 현재 파일의 `relation_text_ko`/review 메모를 따로
  기록해두거나(예: 이 대화에서처럼 직접 기억, 또는 diff 저장), 재실행
  직후 다시 채워 넣을 계획을 세워둘 것
- 가능하면 relation_text_ko를 코드가 아니라 **원본 쪽에 직접** 넣는 걸
  선호할 것(예: `raw_data_정인지/*.json`의 `description_ko` 필드 -
  이건 원본이라 재실행해도 안 날아감). 영문 소스 기반 번역처럼 원본에
  못 넣는 경우만 재실행 후 재작업이 불가피함
- 새 원본을 추가할 때는 되도록 기존에 이미 검수/보강해둔 장소와 안
  겹치는지 먼저 확인(같은 장소가 다른 표기로 다시 들어오면 2번 항목의
  중복 탐지에 걸릴 수 있음 - 아래 참고)

### 1b. 몇 건만 직접 추가 (전체 재실행 없이)

이미 검수 끝난 도시 파일에 새 장소 몇 건만 보태고 싶을 때 쓰는 방식
(2026-08-25 부산에 visitbusan.net 기사 2건을 이 방식으로 추가하며 확립).
전체 재실행과 달리 **기존 파일의 수동 작업을 전혀 건드리지 않는다**:

1. `build_dataset`의 헬퍼를 직접 불러 카카오 키워드 검색만 호출:
   ```python
   import build_dataset as bd, os
   bd.load_env()
   api_key = os.environ.get("KAKAO_REST_API_KEY", "").strip()
   docs = bd.kakao_keyword_search("부산 <장소명>", api_key)
   ```
   결과 상위 후보의 `category_name`/주소가 기대와 맞는지 확인. **후보가
   여러 개인데 이름이 정확히 일치하는 게 하나도 없으면(예: 같은 주소에
   비슷한 이름 업체 여러 개) 억지로 고르지 말고 그 장소는 보류** - 확신
   없는 매칭을 채우지 않는다는 원칙은 자동 파이프라인이든 수동 추가든
   동일하게 적용됨.
2. Kakao 응답의 `x`(경도)/`y`(위도)로 Place 딕셔너리를 직접 조립 -
   `Data_Preprocessing_Template.ts`의 모든 required 필드를 채울 것
   (특히 `place_id`는 `{artist_id}-{category}-{영문슬러그}` 규칙 지키기,
   `status`는 `draft`, `source_url`은 실제 링크 또는 `has_credible_
   citation()` 통과하는 인용문).
3. 기존 `generated_places_<city>_<owner>.json`을 읽어서 새 항목을
   append하고 다시 저장. artist가 이미 있으면 `generated_artists_*`는
   안 건드려도 됨, 새 아티스트면 그것도 추가.
4. review CSV는 필요한 경우에만(예: 매칭이 불확실하면) 직접 한 줄
   추가 - 이 경로는 build_schema()를 안 거치므로 review_notes가 자동으로
   안 생긴다는 걸 기억할 것.
5. 기존 항목의 내용을 이번에 얻은 더 나은 정보로 갱신하고 싶으면
   (예: 더 구체적인 relation_text) 그냥 해당 place_id를 찾아 필드를
   덮어쓰면 됨 - 이것도 원본이 아니라 생성물을 직접 고치는 거라, 나중에
   1a로 그 도시를 통째로 재실행하면 이 개선분도 같이 날아간다는 점은
   동일하게 적용됨.

## 2. 구조적 스캔 (사람이 하나씩 보기 전에 먼저 자동으로 걸러낼 것)

이전 세션에서 아래 스캔들이 실제로 진짜 버그/오염을 잡아냈다. 매번 다
돌려라:

**a) 좌표 완전 일치 기준 중복 탐지** — merge_places()는 이름 유사도로만
병합해서, 언어가 다른 같은 장소(예: "Front Seoul" vs "프론트서울")를
놓친다. 반드시 좌표 기준으로도 확인:
```python
from collections import defaultdict
by_coord = defaultdict(list)
for p in places:
    by_coord[(round(p['latitude'],5), round(p['longitude'],5))].append(p)
# len(v) > 1 인 것들 확인 - 진짜 같은 장소면 artist_ids 합치고 relation_text
# " / "로 합쳐서 하나로 병합, place_id는 더 나은 쪽(실제 링크 있는 쪽 등) 유지
```

**b) 숙소/이벤트성 장소 이름 기반 재검사** — 카테고리 필터를 믿지 말고
이름에 호텔/리조트/펜션/경기장/돔/아레나 등 키워드가 있는지 별도 스캔
("스테이지"/"스테이블" 같은 오탐 주의 - "스테이" 부분 문자열만 보고
판단하지 말 것). 진짜 숙소/이벤트장이면 README "장소 포함/제외 기준"대로
행 자체를 삭제하고, 그 아티스트가 장소 0개가 되면 artists.json에서도 뺀다.

**c) 이름/카테고리/relation_text 정합성 스캔** — 케이팝 성지가 될 수 없는
업종(병원/치과/부동산/학원/은행/관공서 등)으로 매칭되는 건 이제
`NOISE_CATEGORIES`(build_dataset.py)가 자동으로 걸러낸다(2026-08-25 확장 -
"UN Village"가 치과의원에 매칭됐던 사례가 계기). 새로운 업종의 오매칭을
발견하면 이 목록에 키워드를 추가해서 앞으로 자동으로 걸리게 할 것 - 매번
사람이 눈으로 다시 발견하게 두지 말 것. 다만 **카테고리 자체는 그럴듯한데
이름만 다른 경우**(산인데 이름이 비슷한 실내 클라이밍짐 지점에 매칭,
부산시민공원인데 온천천시민공원에 매칭)는 이 필터로 못 잡는다 - 진짜
같은 곳인지는 결국 웹 검색+문맥 이해가 필요해서 완전 자동화가 안 됨
(build_dataset.py엔 웹 검색 API가 안 붙어있음). 그래서 place_name_ko/en/
category/relation_text를 한 줄로 쭉 뽑아 눈으로/WebSearch로 훑는 이 단계
자체는 계속 필요하다. 확신 있는 건 바로 review 사유로 남기고, 애매한 건
AskUserQuestion으로 확인.

새 필터를 추가한 뒤엔 **캐시된 지오코딩 결과부터 다시 훑어서 이미 들어간
데이터 중 새로 걸릴 게 있는지 확인할 것**(`preprocessed/.geocode_cache.json`
순회하며 `NOISE_CATEGORIES`에 걸리는 항목 찾기) - 전체 재실행 없이도 할 수
있고, 있으면 1b 방식으로 직접 제거/교체하면 됨.

**d) 콘텐츠 혼입 스캔(번역/보강 중 자연히 드러남)** — relation_text에
다른 아티스트의 곡/콘텐츠명이 섞여있는지("S-Class"가 BTS 자리에 있는데
사실 스트레이 키즈 곡인 식). 발견하면 relation_text에서 그 부분은
빼고, review 사유로 재확인 요청 남김.

**e) `category_hint` 원본 오염(raw_data_정인지류 소스 한정)** — "촬영지"
같은 폐지된 관계 라벨이 카테고리로 남아있으면 원본 JSON 자체를 고친다
(코드가 아니라 데이터 수정 - `CATEGORY_TO_TS`가 매번 같은 실수를 반복
안 하게).

**f) city 오배정 의심** — 지오코딩이 도시 자체를 잘못 배정할 수 있다(감천
문화마을이 경상북도로 잘못 들어간 사례). 특히 비MVP 지역 결과에 유명한
서울/부산/인천 지명이 섞여 있으면 의심.

## 3. 콘텐츠 보강

**relation_text_ko 없는 행**: 기존 relation_text_en(주로 xlsx의
"Connection/Notes" 열, 또는 팬 콘텐츠 인용)을 사실 기반으로 번역해서
채운다. 여러 사실이 " / "로 이어진 경우 각각 번역해서 유지. 번역 중
발견한 콘텐츠 혼입(2d 항목)은 여기서 걸러낸다.

**한쪽 언어 이름만 있는 행**: 체인/브랜드/공공장소는 아는 대로 채우되,
확신 없으면 WebSearch로 실제 상호 확인. 애매한 소규모 개인 업체는 표준
로마자 표기로 채우고 review에 "실제 영문 간판 미확인" 명시(검증된 것과
안 된 것을 절대 섞어서 표시하지 말 것). 새 영문명이 생기면 **place_id도
그 슬러그로 다시 지어서** 스키마의 "로마자 슬러그" 규칙을 지킨다(한글
그대로 슬러그화된 place_id를 방치하지 말 것) - place_needs_review.csv의
해당 place_id도 같이 갱신.

## 4. source_url 신빙성 재확인

**"실제 출처 URL 없음" 행이 많이 쌓여있으면 사람이 하나씩 찾기 전에 먼저
`naver_hub.py fill-sources --city=<city> --owner=<owner>`를 돌려볼 것**
(2026-08-27 추가, `.env`에 `NAVER_HUB_CLIENT_ID`/`NAVER_HUB_CLIENT_SECRET` 필요 —
README "NAVER API HUB 연동" 절 참고). NAVER 블로그/웹문서 검색으로 자동으로 찾은
링크는 `auto_found_unverified` 상태로 표시되고 review 행이 지워지지 않으니, 그
다음에 사람이 그 링크들을 열어서 실제로 맞는 내용인지 확인하는 절차는 그대로
필요하다 — 이 도구는 "찾는" 수고를 줄여줄 뿐 "확인하는" 절차를 대체하지 않는다.

`has_credible_citation()`(build_dataset.py)이 이미 자동으로 "인물+구체적
콘텐츠명" 있는 relation_text는 `"[콘텐츠 인용 - 링크 미확인] ..."`로
전환하고 review 표시를 뗀다 - 대부분 손댈 필요 없음. 다만 이 휴리스틱은
키워드 목록 기반이라 새로운 콘텐츠 포맷(새 예능 프로그램명 등)은 못 잡을
수 있다 - PENDING으로 남은 항목 중 실제로는 신빙성 있는데 놓친 게 있는지
한 번 훑고, 있으면 `CREDIBLE_CONTENT_MARKERS`에 키워드를 추가한다.
기준을 헷갈리면 README "가장 중요한 규칙 — 출처 검증 게이트" 절 재확인
(요지: 인물+콘텐츠명 있으면 링크 없어도 통과, 날짜는 불필수, "Reportedly"
류 자기부정 문구나 콘텐츠 근거 자체가 없는 맨주장은 불통과. 통과해도
status는 draft 유지 - verified 승격은 여전히 사람이 실제로 확인해야 함).

키워드를 추가할 때 짧고 흔한 토큰(`ig`, `mv`, `ep` 등)은 `CREDIBLE_
CONTENT_MARKERS`(부분 문자열 검색)가 아니라 `CREDIBLE_CONTENT_WORD_
MARKERS`(단어 경계 검색)에 넣을 것 - 부분 문자열로 넣으면 "Vernon IG"처럼
문장 맨 끝에 와서 뒤에 공백/쉼표가 없을 때 못 잡거나(2026-08-25에 실제로
발견), 반대로 "tour schedule"처럼 너무 흔한 단어에 오탐이 날 수 있다
(" tour"를 넣었다가 이 문제로 뺀 적 있음 - 구체적 투어명("Sev Sev Tour")은
긴 문구로 등록해서 살려둠).

## 5. 사람 확인이 필요한 것 vs 바로 처리할 것

이미 README에 문서화된 확정 정책(숙소/이벤트 제외 기준, i-dle/NCT
캐노니컬명, source_url 신빙성 기준, 파일명 규칙 등)은 **다시 물어보지
말고 바로 적용**한다. 반면 아래는 매번 사람 판단이 필요해서
AskUserQuestion으로 확인:
- 처음 보는 유형의 이벤트성/숙소 애매 케이스(카테고리 명확치 않을 때)
- 오매칭 의심인데 완전히 확신은 안 서는 경우(좌표 유지 vs 삭제)
- 콘텐츠 혼입 발견 시 relation_text를 어디까지 남길지
- 새로운 도시/지역으로 스코프를 넓히자는 지시가 나왔을 때 - MVP(서울/부산/
  인천) 범위인지 "전국 확장 준비"용 가벼운 작업인지 반드시 확인(README
  "MVP 이후" 절 참고, CLAUDE.md에 최신 담당 범위 명시돼 있음)

**⚠️ review 플래그를 해제할 자격이 생기면 그 자리에서 바로 CSV도 고칠
것 - 나중으로 미루지 말 것.** 조사/검색/새 소스 확인으로 의심이 실제로
풀렸는데 review CSV를 안 고치고 넘어간 적이 실제로 여러 번 있었음
(2026-08-25 - 부산 뉴진스 3건을 visitbusan.net으로 확인해놓고 플래그를
안 뗌, 좌표 완전 일치로 병합한 서울 3건도 마찬가지). 판단 기준:
- **떼도 됨**: 독립된 두 쿼리(예: 영문 쿼리 + 한글 쿼리)가 같은 좌표에
  수렴했거나, 실제 원본 소스(기사/공식 페이지)로 이름·위치가 직접
  확인된 경우
- **떼면 안 됨**: 원래 서로 다른 두 좌표 중 하나가 틀렸었고 그중 하나를
  판단으로 골라낸 경우(예: 서울숲/홍릉시험림 사례) - 이건 사람 판단이지
  독립적 재확인이 아니라서 여전히 확인 필요로 남겨야 함
- 헷갈리면 review CSV를 최소 한 번 더 열어서 이번에 손댄 place_id들이
  아직도 맞는 사유로 남아있는지 눈으로 확인하고 끝낼 것

**⚠️ `_review_notes`가 완전히 비면 그 행 자체를 CSV에서 지울 것 -
notes만 비워두고 행을 남겨두지 말 것.** 플래그가 다 해소돼서 더 볼 이유가
없어진 행은 needs_review CSV에 남아있을 이유가 없다(2026-08-26 확정).
빈 notes 행 일괄 삭제:
```python
kept = [r for r in rows if (r.get("_review_notes") or "").strip()]
```

**`_todo` 열은 정인지님이 직접 코멘트/링크를 다는 수동 작업용 열이다
(2026-08-26 추가) - 스크립트로 `_review_notes`를 읽고 다시 쓸 때 이 열은
절대 건드리지 말 것.** `csv.DictWriter`로 다시 쓸 때 fieldnames에
`_todo`가 포함돼 있는지, 각 행의 `_todo` 값을 그대로 보존하는지 반드시
확인(빈 문자열로 덮어쓰지 않게). 이 열에 적힌 내용을 읽고 그대로 작업에
반영하는 건 괜찮지만, 임의로 지우거나 자동 판정 결과로 덮어쓰지 않는다.
