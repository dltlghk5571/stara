# 영문 쿼리 지오코딩 매칭 검증

## 이 플래그가 왜 붙었는지 (전제)

`geocode_and_fill_names()`는 지오코딩 시작 시점에 `had_korean_name = bool(row.get("place_name_ko"))`만
보고, 없었으면 `f"{city_en} {name}"`(영문)을 그대로 카카오 "키워드 장소검색"에 넣는다. 이 검색은
문자열 정확 일치가 아니라 한국어 기반 관련도 알고리즘이라, 영문 쿼리를 넣으면 발음·철자가 비슷한
완전히 다른 업체나 동명이인 장소에 매칭될 수 있다. 매칭 결과가 도시명·카테고리 필터를 통과해도
그게 "찾던 그 장소"라는 보장은 없다 — `pick_best_match()`는 숙소/병원 같은 명백한 오분류만 거를
뿐, 실제 동일 장소인지는 검증하지 않는다. 그래서 매칭 성공 여부와 무관하게, 애초에 한글명이 없어서
영문으로 검색해야 했다는 사실 자체 때문에 이 플래그가 붙는다.

## 지난 스킬(fill-bilingual-place-names)과의 차이

방향이 반대다. 그 스킬은 "한글명은 확실히 있는데 영문명이 없는" 경우(카카오 검색 자체는 한글로
안전하게 이루어짐)를 다룬다. 이 스킬은 "애초에 한글명 자체가 없어서 좌표 탐색을 영문으로 해야
했던" 경우를 다룬다 — 좌표 정확성이 걸린 문제라 훨씬 근본적이고, 단순히 영문명 필드 하나를
채우는 게 아니라 **기존 좌표가 맞는지 자체를 재검증**해야 한다.

## 검증 절차 (반드시 이 순서로, 임의로 건너뛰지 않음)

### 1단계 — 한글명 복원 시도 (근본 해결책)

카카오 검색을 영문으로 할 수밖에 없었던 원인 자체를 없애는 게 최선이다. 아래 소스에서
독립적으로 한글명을 찾는다:

- 이 행의 원본 소스(`source_url`, `raw_data_*` 원본 파일)에 한글명이 문맥에 같이 언급돼 있는지
  다시 확인 — 영문 소스라도 지명은 한글로 병기된 경우가 많다.
- 웹 검색으로 `{place_name_en} 한글`, `{place_name_en} 위치` 같은 쿼리를 넣어 한국어 지도/블로그에서
  이 장소를 부르는 실제 한글 표기를 찾는다.
- 관광지급이면 TourAPI 영문 서비스에서 같은 `contentId`로 국문 서비스를 역조회한다(지난 스킬과
  동일한 방향).
- 카카오맵/네이버맵에서 영문명으로 직접 검색해봤을 때 지도 UI 자체가 보여주는 한글 표기를 확인한다
  (카카오 키워드 API 결과가 아니라 지도 검색 UI 쪽 — 둘은 다른 경로다).

### 2단계 — 한글명을 찾았으면: 재검색 + 좌표 대조

찾은 한글명으로 카카오 키워드 장소검색을 다시 돌려 새 좌표를 얻고, 기존(영문 검색으로 얻은)
좌표와 거리를 비교한다. **카카오 대신(또는 추가로) `naver_hub.naver_local_recheck()`(NAVER
API HUB 지역 검색, 2026-08-27 추가 — `naver-api-hub-integration.md` 참고)도 같은 용도로 쓸 수
있다 — 카카오와 독립된 별도 소스라 교차검증 가치가 있다.** 좌표 변환(mapx/mapy -> WGS84)은
2026-08-27에 실제 API 응답(교보문고 광화문점)으로 검증 완료 — 문서에 적혀 있던 KATEC(TM128)
변환은 틀린 정보였고, 실제로는 그냥 위경도 × 10^7 정수라 `naver_hub.py`에서 이미 올바르게
나눠서 반환한다. 카카오 재검색과 동일한 3단계 판정 기준을 그대로 적용한다:

- **100m 이내** → 같은 건물/장소로 간주, `confirmed_same`으로 판정. 기존 좌표 유지, 플래그 해제
  가능. 단 "무엇으로 재검증했는지"는 반드시 기록에 남긴다.
- **100m~500m** → 애매한 구간. 자동으로 판정하지 않고 `ambiguous`로 남겨 사람 확인 큐로 보낸다.
- **500m 초과** → `confirmed_mismatch`. 기존 좌표는 오매칭이 거의 확실하므로, 새로 찾은 한글명
  기준 좌표로 교체를 제안하되 실제 교체는 사람이 최종 확인한 뒤 반영한다.

### 3단계 — 한글명을 못 찾았으면: 문맥 대조로 독립 검증

한글명이 끝내 안 나오면, 기존 카카오 매칭 결과를 그대로 믿지 말고 **다른 근거로 교차 검증**한다.
같은 카카오 API 응답을 다시 들여다보는 건 순환 검증이라 의미가 없다.

- 원본 소스(relation_text, source_url 본문)에 언급된 구체적 단서(동네 이름, 근처 랜드마크,
  층수, 특징적 외관 등)와 카카오가 매칭한 후보의 주소·카테고리·이름이 실제로 들어맞는지 대조한다.
- 단서가 서로 어긋나면(예: 원본은 "홍대 근처"인데 매칭 결과 주소가 다른 구) 재검색 없이도
  `confirmed_mismatch`로 판정할 수 있다.
- 대조할 단서 자체가 원본에 없어서 맞는지 틀린지 판단할 근거가 없으면, 억지로 결론 내지 않고
  `unresolved_insufficient_evidence`로 남긴다. 이 경우는 사람이 원본을 다시 읽어야 하는 진짜
  수동 검토 대상이다.

## 절대 하지 말 것

- 카카오 API가 "매칭에 성공했다"는 사실 자체를 검증 근거로 쓰지 않는다 — 그게 애초에 이 플래그가
  붙은 이유이므로 순환 논리가 된다.
- `confirmed_same`이든 `confirmed_mismatch`든, 근거(재검색에 쓴 한글명 / 대조한 문맥 단서)를
  같이 기록하지 않고 판정만 내리지 않는다.
- `draft`/`verified`/`published` 상태를 이 검증만으로 승격시키지 않는다. 이 스킬은 좌표 신뢰도를
  판정하는 것이지 출처 검증 게이트(relation_text의 verified 승격)와는 별개다.
- 애매하거나 근거 부족한 행을 임의로 `confirmed_same` 쪽으로 밀어 처리 건수를 늘리지 않는다.
  `ambiguous`/`unresolved`로 정직하게 남기는 게 잘못된 확신보다 낫다 — 좌표 오류 하나가 퀘스트
  인증 전체를 깨뜨리는 구조이기 때문이다.

## 출력 형식

각 행마다 아래 정보를 review 큐(`places_needs_review.csv` 또는 동급 파일)에 기록한다:

- `verification_result`: `confirmed_same` / `confirmed_mismatch` / `ambiguous` / `unresolved_insufficient_evidence`
- `verification_method`: `korean_name_recheck` / `contextual_cross_check` / `naver_local_recheck`
- `evidence`: 재검색에 쓴 한글명, 또는 대조한 문맥 단서와 그 출처
- `distance_m`: 2단계를 거쳤다면 기존 좌표와 새 좌표 간 거리

기존 스키마 필드명·구조는 건드리지 않는다 — 이 결과는 검수용 부가 정보이지 정본 데이터 필드가
아니다. 처리 후에는 전체 건수 중 `confirmed_same` / `confirmed_mismatch` / `ambiguous` /
`unresolved` 각각 몇 건인지 요약해서 보고한다.
